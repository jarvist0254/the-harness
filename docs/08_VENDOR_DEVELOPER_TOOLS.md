# Vendor developer tools — Windows qualification, 2026-10-04

Current results: the existing AMD HIP toolchain executed a verified native 1 MiB affine kernel on gfx1036. The locally extracted official Intel DPC++ compiler is callable and compiles a SYCL fixture, but its OpenCL adapter excludes both current NVIDIA/AMD platforms, so SYCL GPU execution is NOT_CHECKED. Separately, Intel-authored OpenCL benchmark tools were built from a clean pinned export and verified 1 MiB upload/readback on both installed GPUs. These distinct results do not establish Intel hardware, four-card execution or direct P2P. No result in this document bears on cross-vendor peer capability, which is settled-unsupported on Windows by specification and gated shut on Linux consumer desktops.

## Official options for a separate local SDK

AMD's [TheRock releases guide](https://github.com/ROCm/TheRock/blob/main/RELEASES.md) documents Windows SDK tarballs as raw extracted files with no installation steps, and isolated Python packages. Its [development support matrix](https://github.com/ROCm/TheRock/blob/main/SUPPORTED_GPUS.md) currently includes Windows gfx1036, but explicitly distinguishes development readiness from released-product compatibility. The older [Windows HIP SDK matrix](https://rocm.docs.amd.com/projects/radeon-ryzen/en/latest/docs/shared/hipsdk/reference/system-requirements.html) does not list this APU. Neither page retroactively qualifies the installed June development build or its gfx110X libraries. A future SDK should be a pinned, hash-recorded Windows package with the actual target's kernel/library payload, extracted into a fresh harness directory and used only through a child-local environment.

Intel's [official compiler download page](https://www.intel.com/content/www/us/en/developer/tools/oneapi/dpc-compiler-download.html) documents full compiler package `dpcpp_win-64` via its conda channel. Its pip offerings are runtime packages, so installing `intel-sycl-rt` alone does not obtain a compiler. The [intel/llvm 7.1.1 release](https://github.com/intel/llvm/releases/tag/v7.1.1) describes compiler/runtime archives and states that its Windows configuration omits HIP/CUDA plugins. The latest-release API returned no downloadable assets for that tag during this inventory; no filename was invented.

A concrete official development archive was found through the GitHub releases API: `https://github.com/intel/llvm/releases/download/nightly-2026-10-04/sycl_windows.tar.gz`, advertised size 545,568,109 bytes, with adjacent `.sigstore.json`. Metadata is preserved in `intel_llvm_recent_releases.json`. It was not downloaded, extracted or executed; payload SHA-256 and exact compiler version remain `NOT_CHECKED`. Pinning this nightly is an experimental alternative, not a production recommendation. The [Intel build guide](https://github.com/intel/llvm/blob/sycl/sycl/doc/GetStartedGuide.md) describes Windows CUDA builds with an explicit plugin build; AMD HIP instructions are Linux-specific. The archive must not be presented as an already working cross-vendor Windows runtime.

AMD's [Windows component status](https://github.com/ROCm/TheRock/blob/main/docs/development/windows_support.md) marks ROCprofiler-SDK unsupported. Native-Windows availability of Linux-oriented AMD SMI/profiler tools is not established by installing a Python wrapper. Keep Linux/WSL qualification separate.

For a Windows transfer benchmark without oneAPI, build the pinned `compute-benchmarks` OpenCL targets under existing VS 18, out of source, with `BUILD_OCL=ON`, `BUILD_L0=OFF`, `BUILD_VK=OFF`, `BUILD_SYCL=OFF`. Note that a green Level Zero conformance run proves nothing about cross-card peer access: at the pinned commit 88447c0 — whose entire purpose was "Add new zeDeviceCanAccessPeer scenarios" — every P2P conformance test is vacuous for two distinct physical cards (one asserts only EXPECT_EQ(a2b, b2a), so false == false passes; two call get_p2p_properties with no assertion on the result at all; the new tests assert only trivial self-peer cases), and all GTEST_SKIP() when device count < 2. **A full PASS on a single-GPU machine is indistinguishable from a full PASS on a qualified four-card machine.**
4. For an eventual Intel card, extract a verified official compiler/runtime archive into a fresh local directory, set PATH/LIB only in the launched child, then record `clang++ --version`, `sycl-ls` and Level Zero device results. An Intel device and compatible graphics driver must exist before an Intel hardware PASS. The current host has neither measured Intel GPU execution nor a located Intel developer CLI. **Plan the Intel arm on Linux.** Windows is unqualified for multi-Arc peer access: ze_peer is excluded on non-UNIX by upstream build configuration (if(UNIX) add_subdirectory(ze_peer) else() message(WARNING "Skipping ze_peer: test only supported on Linux")), its source uses fork(), socketpair(PF_UNIX), sigaction() and passes a dma-buf fd via SCM_RIGHTS, and Intel's own collateral is written entirely in Linux terms. level-zero-tests builds on Windows; **the P2P benchmark inside it does not.** A Windows DPC++/sycl-ls/Level Zero inventory is a compiler-and-enumeration gate only — it can never produce an Intel **peer-access** PASS. If Intel hardware is funded, the qualified path is 2+ Arc Pro B60/B70, same generation and family, Linux, kernel >= 7.1 (7.1.2 verified) + intel-compute-runtime >= 26.22 (26.22.38646.4 verified), PCIe ACS and IOMMU disabled (Intel doc 863931 §2.0: "ACS would route all the data transfer back to the root complex... Both features would block the P2P transfer"), and NEOReadDebugKeys=1 RenderCompressedBuffersEnabled=0 for multi-device workloads — without it P2P reads return garbage while reporting success. **A PCIe switch is not the gate:** the gate is the kernel chipset allow-list plus BIOS ACS/IOMMU state, and an AMD Zen host (family >= 0x17) passes it without one — 2× Arc Pro B60 verified peering on an ordinary AMD AM5 / PCIe 5.0 board at x8 (intel/compute-runtime#921 comments 16, 27), which is the class of the existing MSI PRO X870-P WIFI host, so no switch chassis is needed for an Intel Arc arm. A switch is only required where the root complex is not allow-listed, notably consumer Intel desktop chipsets. The Ubuntu 24.04.3/.4 fresh-install pin, "behind one PCIe switch or on one PCIe root", "Re-Size BAR enabled" and the multi-arc-bmg-offline-installer-26.18.8.2-combo pin are not supported by either vendored Intel source. Bifurcated x4 branches remain a poor P2P layout: four separate CPU root ports each needing to pass the gate, and Intel's ~20 GB/s uni / 40 GB/s bi calibration is for Gen5 x8, not Gen4 x4.

These are concrete build paths and remaining gates. Enumeration, compilation, kernel correctness, math-library support, physical capacity and sustained performance must each receive separate statuses.

## Follow-up execution — local HIP kernel and extracted Intel compiler

This section supersedes the initial inventory's pending download/kernel statuses. All sources and attempts are retained under `records/vendor_cli_qualification_20261004/`; extracted Intel tools are under `records/toolchains/intel_sycl/`.

**Native AMD computation passed.** Initial combined HIP host/device compilation failed because HIP's Clang math wrappers conflict with MSVC 14.51 `cmath` declarations (`native_hip/compile.json`). A separate device-only unit compiled with existing hipcc using `--genco --offload-arch=gfx1036 -D__HIPCC_RTC__ -O2`, avoiding host standard-library headers. This experimental RTC header configuration is recorded explicitly; no GPU architecture override or SDK edit occurred. A VS18 host launcher compiled with `__HIP_PLATFORM_AMD__` uses checked HIP module APIs to load the actual gfx1036 code object, allocate one 1,048,576-byte buffer, upload 262,144 FP32 values, launch the affine kernel, synchronize and read back every value.

`native_hip/runs.json`: default exit 0, zero mismatches, max absolute error 0, kernel completed, actual integrated gfx1036 at PCI bus 116. Corruption changes real readback element 12,345 before comparison: exit 1, one mismatch, maximum error 1. This checks the verifier rather than injecting a hardware fault. The test-before-source failure and both unsuccessful compiler configurations are preserved. Each execution has external 60-second supervision. This qualifies one native HIP affine kernel, not rocBLAS, llama.cpp HIP, dedicated VRAM, multi-device HIP or performance.

**Intel tools are callable; compilation passed; GPU execution is NOT_CHECKED.** Official nightly archive: 545,568,109 bytes, SHA-256 `ec02b21bfffc142765633b4d9ab5ced9a2b4e088d9250ceb8cff05c34d71ef49`, matching GitHub API digest. Extraction validated containment, regular-file/directory types and size bounds: 961 members, 1,428,868,004 expanded bytes. No downloaded scripts were executed and the extracted tree was not edited. PATH/LIB additions were child-local only.

Actual version is DPC++ `7.2.0 (pre-release) (Nightly 2026-10-04)`, Clang `24.0.0git`, commit `b98b3a76c11345f1ff6f295e416755ce8c11b60c`. Both fixture modes exit 2 with NOT_CHECKED, no allowed NVIDIA/AMD OpenCL GPU, CPU fallback forbidden. No Intel physical GPU is present.

Two child-local loader probes preserved in `intel_opencl_probe*.json` confirm successful loading of System32 OpenCL.dll, missing optional CUDA/HIP adapters, and a ZE_RESULT_ERROR_UNINITIALIZED return from Level Zero. **That result is a NO_DRIVER_INSTALLED outcome and carries zero information about Windows peer capability**: zero Intel GPUs means no Intel graphics driver, means no ze_intel_gpu64.dll, means nothing for the loader to bind to — which is its documented graceful-failure behaviour. The probe also used a **self-built** loader rather than the Intel-shipped pair. Do not cite this as evidence about Windows Level Zero peer support (doc 10 §1.7). The first probe exposed a Windows path-quoting error; the second used the documented quoted `UR_ADAPTERS_SEARCH_PATH` format and still found zero platforms. Exact-commit [Intel OpenCL adapter source](https://github.com/intel/llvm/blob/b98b3a76c11345f1ff6f295e416755ce8c11b60c/unified-runtime/source/adapters/opencl/platform.cpp) explicitly filters `NVIDIA CUDA` and `AMD Accelerated Parallel Processing`, matching both installed platforms. The pinned source snapshot is retained. This explains the discrepancy with PyOpenCL. No loader flag removes that compatibility filter; System32 OpenCL.dll is not a UR adapter and must not be force-loaded as one. See [official UR discovery documentation](https://oneapi-src.github.io/unified-runtime/core/INTRO.html). A separate compatible CUDA/HIP SYCL adapter build would be another qualification effort.

The correct Windows Sigstore bundle was fetched and its hash matches GitHub metadata (`windows_signature_provenance.json`). Cryptographic signature verification is NOT_CHECKED: no verifier was installed. Initial generic bundle selection mistakenly fetched the unrelated Linux bundle; it remains preserved and explicitly does not attest the Windows archive. Official-metadata digest agreement and retaining the correct attestation are separate from cryptographic verification.
