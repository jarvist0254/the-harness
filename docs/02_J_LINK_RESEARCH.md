# J-Link: aggregate VRAM across vendors

Research date: 2026-10-04. Findings are grounded in the pinned repositories and primary sources listed in 05_PRIMARY_SOURCES. Proposed extensions are identified below; none has been GPU-qualified here. Extended by 10_JLINK_CROSS_VENDOR_P2P_VERDICT_AND_PLAN.md (2026-10-05), which **promotes Ideas 2 and 3 below from "fallback" to the route**, closes eight transport families as settled-unsupported, and records the measured host inventory.

Target: four external 8 GB cards, with 32 GB nominal aggregate dedicated storage before per-card overhead. The existing 16 GB RTX 5070 Ti is an optional separate fifth participant, not one of the four external cards. Neither population creates a general contiguous allocation automatically. Official NVIDIA regional product pages list NVLink as No for RTX 5050, RTX 5060 and RTX 5070 Ti (S23-S25); PCIe P2P remains a separate, unqualified capability.

## What pooling can mean

| Meaning | What the application sees | First-release feasibility |
|---|---|---|
| Capacity inventory | Per-device free memory and a summed total | Straightforward, but no execution benefit by itself |
| Task/model pool | Different tasks/models resident on different cards | Good PyRe/J-Link baseline; an individual model must fit its assigned card |
| Sharded model/tensor pool | One workload's ordered blocks live on multiple cards | Best route for one larger model; needs backend/operator support and transport |
| Transparent allocation pool | An arbitrary existing GPU program allocates one buffer across every vendor | **No supported general solution exists.** SETTLED-UNSUPPORTED on Windows by specification and on Linux consumer hardware as of 2026 — not merely "not established by this research" (§1.1, §1.8) |

The target is useful sharded capacity plus reliable task placement. Do not promise that an unchanged CUDA program can allocate Intel or AMD memory. CUDA/HIP/Level Zero pointers belong to their runtime/context; handles and logical object IDs are safer cross-worker interfaces.

## Idea 1 — One Vulkan process, explicit layer placement

Build llama.cpp with Vulkan. Enumerate devices, choose one representation per physical card, and try layer splitting across selected Intel/AMD/NVIDIA devices. The shared API reduces the runtime integration surface. This is the first mixed-vendor experiment, not a support guarantee for every SKU or operator.

Pinned code evidence: ggml-vulkan-buffers.cpp implements inter-device copies through a source host staging buffer and destination write; ggml-vulkan.cpp refuses cross-device async copies; ggml-backend.cpp has synchronized host-copy fallbacks. This supports a plausible portable route, with a bandwidth and synchronization cost. Vulkan device groups are **impossible** for mixed vendors by specification (VUID-VkDeviceGroupDeviceCreateInfo-pPhysicalDevices-00376); always use separate device objects.

Proposed J-Link addition: identify cards by PCI address/UUID, reserve display/workspace/KV overhead, calculate placement, launch with explicit devices and record peak memory/output parity. Start with whole layers. If one layer cannot fit any device, reject or use a separately supported tensor-split/offload path. A summed free-memory number cannot solve an indivisible oversized layer.

## Idea 2 — Vendor-native workers joined by ggml RPC

Use separate CUDA, HIP and SYCL builds/processes. Each worker owns its allocations and kernels; a coordinator targets exposed ggml devices. Same-host experiments can use loopback endpoints on different ports. This isolates runtime dependencies and creates a natural future multi-host/pod boundary.

The current RPC README supports device exposure, multiple endpoints and distributed placement; it explicitly calls RPC fragile and insecure. Keep initial endpoints on loopback. The Windows launch script binds 127.0.0.1 and opens no firewall rules. For later multi-host work, design authenticated transport separately; TCP or RDMA does not provide application authorization by itself.

Potential advantages: vendor optimized kernels; individually replaceable workers; flexible OS boundaries. Costs: serialization, tensor transfer, coordinator CPU/RAM, operator incompatibilities, protocol-version coupling. All workers/coordinator must use the pinned commit initially. Do not equate multiple independent HTTP chat servers with sharding one model—those are complete-model task workers, not tensor workers.

## Idea 3 — PyRe workload graph with a host tensor bridge

For Python/scientific work outside GGUF inference, propose a J-Link graph contract: each stage declares supported backend, tensor shape/dtype/layout, workspace, peak allocation and semantic tolerance. CUDA/HIP/SYCL workers execute whole stages; the coordinator moves bounded buffers through host memory with sequence numbers and explicit completion.

Represent a tensor as object_id, owning worker/device, shape, dtype, byte count, generation and checksum—not a foreign raw pointer. Begin with copy semantics. Later investigate registered shared host rings/double buffers, but confirm each runtime's registration and synchronization requirements. Avoid assuming pinned pages created by one vendor are automatically portable to all others.

Prioritize coarse stages with large compute per boundary byte: layers, tiles, chunks, specialist/expert blocks or independent simulations. Fine-grained tensor reductions across consumer x4 links may lose to a single GPU. Transfer-inclusive parity and throughput determine promotion.

## Idea 4 — Residency tiers and expert routing

Proposed extension: keep frequently used specialists/layers on the fastest card, cold objects on high-capacity cards or bounded host RAM; route work to data and migrate only when profitable. This matches the recovered adaptive-compute/cluster-shell direction without requiring a unified address space.

Expert residency across cards is genuine aggregate model storage if the model has compatible routed execution, but expert movement and routing still cost time. Disk offload and Windows shared GPU memory are separate tiers and must not be reported as dedicated VRAM. KV capacity depends on architecture, context and active sequences; measure it. Dense, MoE and state-space models need different planners.

## Transport and portability method matrix

Installed-host evidence on 2026-10-04: separate NVIDIA/AMD OpenCL kernels passed six directed size cases through explicit host staging, with corruption detected. A corrected Vulkan fixture passed actual NVIDIA GPU fill/readback -> forwarded host bytes -> AMD copy/readback for 256 KiB, with its corruption run rejected. Four CPU-backed ggml RPC workers passed four stages and three transfers. These results establish narrow plumbing paths, not direct P2P, four-discrete-card residency or larger-model inference. A legal D3D12 placed-buffer/shared-heap implementation also passed 256 KiB NVIDIA-to-AMD copying and detected the corruption control. The GPU queue handoff uses a real shared cross-adapter fence. Shared-heap descriptors were recorded; the API's required L0/system-memory backing is not a measured dedicated-VRAM path. The initial committed-buffer E_INVALIDARG was an implementation defect, not a hardware exclusion (S30).

## Hardware-negative qualification plan

Proposed tests only, not hardware PASS results. Directed off-diagonal pairs for n cards = n(n−1): 2 cards → 2, 3 cards → 6, **four external cards → 12**. Adding the display 5070 Ti gives **20 only for a mixed-vendor host-staged matrix** — label it as such. The **Level Zero** directed matrix stays at **12** even with the 5070 Ti installed, because the RTX 5070 Ti is not a Level Zero device at all and no zeDeviceCanAccessPeer pair involving it can be constructed. One working direction does not qualify its reverse. **On the current host the runnable pair count is zero** (one discrete GPU installed).

1. Record PCI BDF/UUID/LUID, OS, driver/runtime, memory budget, link width/speed and root/chipset/switch paths. Deduplicate native/Vulkan/RPC aliases. Discover without BIOS, driver or kernel changes.
2. Record directed CUDA/HIP/Level Zero capability queries, enablement errors, atomics and allocation limits. Unsupported access must reject or select staging; never force foreign-pointer dereference.
3. Compare peer-enabled, peer-disabled and explicit pinned host two-hop copies at 8 KiB, 4 MiB, 64 MiB and bounded larger buffers. Warm up, synchronize, verify patterns/checksums and test concurrent transfers. Require transport/residency evidence; bandwidth alone is insufficient. Mandatory controls (§2.4 N1–N13): **N1** host-staged two-hop at the same sizes must be materially slower (~3 GB/s vs ~28 GB/s peer, ≈9×) — **if a "P2P" number is at or below the host-staged number, it IS host-staged; this is the single most important control.** **N2** checksum on every transfer, because ZE_RESULT_SUCCESS with 100% corrupt data is a documented reachable state (256 MB zeCommandListAppendMemoryCopy returned ZE_RESULT_SUCCESS while 4,194,304 of 4,194,304 elements came back wrong; Intel acknowledged the misleading error path). N3 query-vs-outcome consistency both directions. N4 ACS-redirect on/off on the same boot. N5 IOMMU on/off. N6 CCL_TOPO_P2P_ACCESS=0 vs =1. N7 same-device ceiling. N8 NEOReadDebugKeys=1 RenderCompressdBuffersEnabled=0 for D2D, without which Intel documents the bandwidth is **doubled** spuriously. N9 cross-generation pair → must refuse. N10 iGPU+dGPU pair → must refuse. N11 consumer-Arc substitution → expect refusal. N12 single-card ze_peak sanity. N13 driver-version regression pair across the installer pin.
4. NVIDIA: CUDA p2pBandwidthLatencyTest and capability matrix, then NCCL correctness/logs with NCCL_P2P_DISABLE negative control. AMD: TransferBench HIP DMA/compute-copy versus staging, then RCCL. TransferBenchCuda is separate. Intel: P2P copy/ring only after successful peer queries.
5. Vulkan: enumerate groups/per-heap features and test small supported imports with matching synchronization/backing checks; unsupported imports fail cleanly. D3D12: buffer/fence round trip, L0 backing measurement and CPU/GPU-copy comparison; system memory is not dedicated VRAM.
6. OpenCL/SYCL: unsupported platform/context/SVM/USM cases reject. DLPack copy=False on incompatible devices rejects rather than claiming zero-copy. dma-buf/RDMA requires distinct exporter/importer/NIC and direct-path evidence.
7. Shard a model larger than each 8 GB card's usable capacity with per-card residency/output parity. Reject oversized indivisible layer, unsupported operator, exhausted reserve, stale worker, missing card and wrong shape/dtype. Independent complete-model servers prove a task pool only.
8. Engine-count ceiling: Intel reports two engines per B60 Pro device (one compute+copy, one copy-only), so a 12-flow full mesh on four cards is **not schedulable**. Intel's own four-card example uses exactly 4 flows. Cap concurrency at min(n·E, available engines) and record the engine map from ze_peer -q first. Tier 3 rings: all (n−1)! distinct directed rings — 2 for n=3, **6 for n=4**. Known tool defect: with -c, per-pair bandwidth is wrong while the total is correct — take per-pair numbers from non--c runs. **A green Level Zero conformance run proves nothing about cross-card peer access** (all P2P tests GTEST_SKIP() when device count < 2).
9. Compare single 5070 Ti, two-card and four-card loading/prefill/decode/transfers/host RAM/thermal results. Capacity and speedup are separate verdicts; optional fifth-card results remain separate.

## Deferred integration candidates

- Cross-vendor P2P through DMA-BUF/external memory: **Windows CLOSED by specification; Linux gated shut by the p2pdma whitelist on consumer desktops.** The single genuinely open item is NVIDIA-VRAM-export → AMD-import with residency measured — nv_dma_buf_attach refuses only *NVIDIA* GPU attachers, not foreign ones, and nv-dmabuf.c does emit BAR1 physical addresses; a third party got working P2P on a Quadro RTX 5000 with an **FPGA** as bus master, but **nobody has published the GPU-as-importer variant**. Highest-value open experiment; needs a patched open kernel module (§1.9 item 1).
- AdaptiveCpp: promising cross-vendor kernel compilation, but compiler portability does not create shared VRAM. Port a narrow kernel only after routing works.
- NCCL/RCCL/oneCCL: useful vendor communication stacks; matching API shapes do not imply one mixed-vendor communicator.
- DDP: usually replicates the model; it does not automatically increase single-model capacity. FSDP/ZeRO/pipeline sharding address different storage costs, mostly within established compatible stacks.
- ZLUDA/translation layers: CUDA compatibility experiments do not demonstrate safe cross-vendor allocation pooling.
- **External PCIe switch chassis** — can move the Linux topology gate (`pci_p2pdma_distance()` success) **for the cross-vendor dma-buf/p2pdma path only**. Requires both GPUs behind one switch, ACS redirect off, IOMMU passthrough. Genuinely open (§1.9 item 2). **Scope limit — do not generalise this:** a switch is *not* the gate for **same-vendor** peer access. For Intel Arc Pro on an AMD Zen host (`family >= 0x17`) the kernel allow-list passes with **no switch at all** — 2× Arc Pro B60 verified peering on an ordinary AM5 / PCIe 5.0 board at x8, and P2P confirmed on AM5 with kernel 7.1.2 + Intel Compute 26.22.38646.4 (`intel/compute-runtime#921` comments 16, 27; doc 10 §1.10, first-hand). A switch is only needed where the root complex is *not* allow-listed, notably consumer Intel desktop chipsets.
- **CXL** — SETTLED-UNSUPPORTED as a consumer-GPU VRAM bridge: coherency is host↔device, not device↔device, and no shipping consumer GPU implements it (§1.5, §1.8 item 5).
- **UALink** — the only standardized cross-vendor direct-memory fabric (load/store + DMA, up to 1024 endpoints), but **NVIDIA is not a member**; silicon in labs H2 2026, products 2027. Structurally cannot bridge to NVIDIA; zero consumer applicability for at least two product generations (§1.5).

## Proposed J-Link contract

Persistent device registry; alias deduplication across Vulkan/native/RPC; timestamped memory samples; per-device leases; topology graph; measured transfer costs; model block residency map; worker heartbeats; deterministic launch manifest; cancellation/drain; output parity; durable resumable task records. PyRe remains the user-facing run controller.

Memory equation per card:

usable = observed free dedicated memory - display reserve - backend/workspace reserve - planned KV/activation reserve - existing J-Link leases.

Do not subtract existing leases twice if an observed free sample already reflects their actual allocations. Distinguish reserved-but-not-yet-allocated bytes from resident bytes; production accounting must reconcile both. The included planner's examples assume the free sample precedes all modeled overhead.

Production admission must acquire all participating leases atomically, then validate fresh samples before launch. If any card fails admission, release the partial reservation and queue/replan. The included planner only proposes placement; it implements no leases or process supervisor.

## Performance reasoning

For each stage, estimate compute duration plus boundary transfer duration. Single-request decode passes sequentially through pipeline stages; four cards do not imply 4x speed. Batched requests may overlap stages if supported. Minimize boundary bytes; place transfer-sensitive stages on CPU-root links before slower chipset paths when measurements justify it.

Illustrative boundary math: 4,096 FP16 values are 8 KiB per token; a 512-token block is 4 MiB. This is only one simple activation shape; real implementations may copy residuals, multiple tensors or workspace. Tensor parallel all-reduces occur more often than contiguous layer boundaries. No speed estimate is released from this arithmetic.


## Working executor plan and independent paper evidence - 2026-10-04

Engineering inference: a Python coordinator executing one residual MLP through separately compiled OpenCL programs, resident stage weights and explicit host-staged activation transfers is a credible experimental baseline. It exercises actual layer partitioning across supported vendor devices rather than merely running independent models. It is a proposed narrow inference executor, not an arbitrary-Python accelerator, transparent allocator or coherent VRAM pool. The current host has ONE discrete GPU (RTX 5070 Ti) plus ONE AMD **integrated** APU (Raphael, shared system memory, no dedicated VRAM); zero Intel GPUs; ze_loader.dll absent. It can test two-vendor **host-staged execution**; it cannot qualify four external dedicated 8 GB cards, and **the AMD iGPU cannot serve as a dedicated-VRAM peer**. Population available for any peer experiment: one discrete card. Directed peer pairs possible: **zero**.

The first model should have a fixed supported graph, for example residual blocks `x + relu(x W1 + b1) W2 + b2`, with deterministic FP32 inputs/weights and an independent CPU reference. Each physical device owns a contiguous nonempty block range and its persistent weights. Compile the same qualified kernel subset independently for each platform. Transfer the actual completed boundary activation through a host array; never reconstruct it from a CPU reference. Finish/wait the source event before uploading to a destination-context buffer, then use only destination-context events for its kernel dependencies. This is same-process orchestration across distinct runtimes. Isolated workers remain a different later deployment mode.

Acceptance evidence for a working narrow executor:

1. Compare each block and final output to the independent CPU reference across multiple seeds, batches and supported dimensions, with declared FP32 tolerances and nonfinite checks. Record actual physical identities, assigned blocks and completed device kernel events. All layers must run on assigned devices; CPU reference execution is outside the measured executor.
2. Record allocations and residency once at initialization, reuse weights across repeated requests, and separate weight-upload traffic from boundary traffic. Record dedicated-versus-shared memory and available budgets; runtime buffer allocation alone does not certify physical dedicated-VRAM residency.
3. Corrupt a real boundary tensor, change a late block's weights and intentionally reorder noncommuting blocks. Each must change results or trigger parity failure. Missing device, duplicate physical alias, unsupported operator, wrong shape/dtype and oversized indivisible block must reject honestly. Do not rerun the known-crashing mixed-platform context control by default.
4. Measure startup, warm execution, source readback, destination upload, host RAM and per-stage compute separately. For FP32 boundary shape batch-by-d, one logical activation contains `4 * batch * d` bytes and ordinary host staging performs both device-to-host and host-to-device legs. Copies of extra residuals/workspace must be included when present. Sequential request latency sums stages and boundary costs; stage overlap and throughput require separate multi-request experiments.
5. First establish small safe two-vendor correctness. A four-card capacity verdict then requires four distinct external dedicated devices, genuinely resident partitioned weights larger than every individual usable budget, per-card allocation/residency evidence and successful inference. A hypothetical budget test or an AMD iGPU's shared RAM cannot satisfy that verdict. Keep the 5070 Ti display card outside external-card capacity unless explicitly opted in.

Passing these gates proves a functioning model-specific mixed-vendor inference pipeline and its measured capacity/transfer behavior on the tested population. It does not prove attention/KV caches, token generation, GGUF loading, training/autograd, optimized GEMM, arbitrary model compatibility, speedup or a physically unified memory space. Those require additional explicit operators, formats and tests. Nothing in the five sources establishes novelty for layer/pipeline partitioning itself.
