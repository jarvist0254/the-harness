## What the pinned code says

`GGML_VK_DISABLE_F16` is presence-based. In `ggml/src/ggml-vulkan/ggml-vulkan.cpp:4272-4274`, any value disables `device->fp16`. Matmul dispatch separately chooses the F16-accumulation pipeline in `ggml-vulkan.cpp:5954-5968`; it returns false immediately for F32 weights (`src0_type == GGML_TYPE_F32`). Thus the admitted `GGML_VK_DISABLE_F16=1` run does not select a different F16-accumulation route for F32 weight matmuls. It does disable the `device->fp16`-guarded subgroup-pipeline registration block (`ggml-vulkan.cpp:2615-2625`). F32/F32 pipeline registration exists under cooperative-matrix-1 support (`ggml-vulkan.cpp:2387-2436`) and a non-cooperative subgroup path (`ggml-vulkan.cpp:2615-2621`); the runtime logs identify NVIDIA as `NV_coopmat2` and AMD as `matrix cores: none`, but do not prove which F32 matmul pipeline each tensor actually selected. Cooperative-matrix-2 registration shown at `ggml-vulkan.cpp:2278-2302` covers F16/F16 and selected quantized types, not F32/F32. The experiment therefore supports a bounded test of fusion/operation ordering; it does not justify a claim that the NV F32 matmuls were using FP16 accumulation.

F32 attention in this fixture uses regular attention rather than Flash Attention: the graph selects `GGML_TYPE_F32` masks when flash attention is off (`src/llama-graph.cpp:39, 820, 2765`), and the regular path sets the attention matmul accumulator to `GGML_PREC_F32` (`src/llama-graph.cpp:2691-2698`). F32 KV tensors are not cast to F16 in this non-Flash path; the casts at `src/llama-graph.cpp:2655-2662` are inside the Flash Attention branch, which the fixture disables.

CPU and Vulkan both use F32 tensors here but have distinct reductions and math functions. CPU RMSNorm accumulates squares in `ggml_float`, then calls `1.0f/sqrtf(...)` (`ggml/src/ggml-cpu/ops.cpp:4140-4148`); the Vulkan RMSNorm shader accumulates float partial sums, reduces within a workgroup, and calls GLSL `inversesqrt` (`ggml/src/ggml-vulkan/vulkan-shaders/rms_norm.comp:80-100`). CPU softmax uses `ggml_vec_soft_max_f32` and `expf` for sinks (`ggml/src/ggml-cpu/ops.cpp:5896-5912`); Vulkan softmax computes `exp` and parallel float workgroup reductions (`ggml/src/ggml-vulkan/vulkan-shaders/soft_max.comp:115-157`). These source differences are plausible contributors to small accumulated discrepancies, but neither source alone establishes the cause of this run's 34 logit mismatches. No pinned shader build option or runtime switch surfaced in this inspection that guarantees correctly-rounded GLSL `exp`/`inversesqrt` or a CPU-identical reduction order.

The CPU backend's F32 type table selects `ggml_vec_dot_f32` with F32 dot inputs (`ggml/src/ggml-cpu/ggml-cpu.c:215-220`). Its SIMD implementation uses architecture-selected F32 vector FMA accumulators and then a vector reduction, with scalar leftovers (`ggml/src/ggml-cpu/vec.cpp:11-137`); the non-SIMD branch accumulates products in `ggml_float`. Therefore “CPU F32” is not a universal double-precision oracle for matmuls: exact accumulation behavior depends on the compiled CPU SIMD path, and Vulkan's F32 shader/pipeline can use a different lane and reduction grouping. This is a mechanism to account for, not proof that it caused this failure.

## Environment switch semantics

`GGML_VK_DISABLE_FUSION` is also presence-based (`ggml-vulkan.cpp:4908-4914`). When set, it disables the backend's recognized multi-op fusions, including multi-add and MatMul+Add sequences in `ggml-vulkan.cpp:14323-14357`, selected TopK fusions (`ggml-vulkan.cpp:13837-13865`), and RMS-related fusion admission (`ggml-vulkan.cpp:12189-12200`). With Flash Attention already disabled, this does not turn Flash Attention on or off. A one-factor rerun with only this child-local variable added would preserve tensors, caches, devices, and tolerances while testing whether fused Vulkan kernels or fused operation ordering contribute to the residual drift. This is the best next diagnostic if admitted; it does not assert fusion is the cause.

`GGML_VK_DISABLE_GRAPH_OPTIMIZE` is presence-based (`ggml-vulkan.cpp:4025-4026`). Its graph-optimization callback returns without reordering when set (`ggml-vulkan.cpp:14676-14683`); otherwise it builds a dependency-aware node order (`ggml-vulkan.cpp:14685 onward`). This changes scheduling/order while leaving each node's operation unchanged. It is a secondary one-factor diagnostic if disabling fusion leaves the same failure: compare logits and verify placement/logs remain complete. It tests sensitivity to independent-node execution order and buffer scheduling, rather than a precision mode.
