## Working-executor acceptance experiment

The user's follow-up makes a working single-workload executor the next acceptance target. Implement it in this harness as an experimental Python/OpenCL sidecar; do not edit the installed PyRe product. Research findings guide the design, but measured execution decides acceptance.

1. Model: deterministic eight-layer FP32 residual MLP, width 512, batch 8, seed 103004. Each layer has unique weights and bias; compute `relu(x + x @ W + b)`. CPU NumPy reference uses the original uncorrupted input and weights. Bounds: width 32–512, batch 1–16, layers 2–16; combined model buffers under 32 MiB. This is a real neural workload, not LLM acceptance.
2. Placement: reuse the pure contiguous planner, round each layer's weight+bias bytes upward to MiB, reserve one MiB for explicit activation/work buffers. Default policy input is nine MiB per device, zero additional reserve: eight MiB modeled layer budget each. These are intentional policy caps, not observed free memory. On two installed devices this assigns four unique layers each. All assigned weights stay resident in their own context before inference; upload each weight once, then forward actual final stage activations to the next context. No whole-model replication or CPU layer execution in the GPU path.
3. Devices: default requires actual NVIDIA and AMD GPUs; optional explicit runtime IDs allow up to four qualified GPUs, including Intel when present. Exclude CPU/software/subdevices. Refuse repeated IDs and known physical aliases. If several selected devices of one vendor lack distinguishable physical identity, refuse the ambiguous selection. Runtime-only identities stay labeled ephemeral; AMD integrated memory stays shared host memory. Missing required devices return NOT_CHECKED.
4. Execution: separate one-device contexts, in-order queues, actual OpenCL kernels, bounded host activation buffers, explicit host staging. GPU events must complete; compare all output elements with independent CPU stages using documented FP32 tolerances. Record allocation bytes, block ownership/hashes, actual kernel counts, upload/copy counts, stage parity and final parity. Do not treat advertised total memory as fresh free memory.
5. Supervision: executable child has an external 60-second deadline; parent records timeout/native exit as FAIL and closes only its own child. Lazy runtime imports keep pure contract tests GPU-free. Atomic JSON results no larger than 128 KiB. No persistent workers or services. No claim of distributed durable replay, production admission leases or driver-overhead measurement.
6. Acceptance: default NVIDIA-to-AMD and reversed AMD-to-NVIDIA runs pass. Corrupt the real activation at the first vendor boundary; run the remaining layers and require final parity FAIL/exit 1 against the original CPU reference. Oversized policy budget, duplicate IDs and unavailable ID cases refuse before allocation with explicit exit 2. Pure tests show a matching four-device workload fits four policy budgets and fails with three, without claiming four-card execution.
7. Final label: MIXED_VENDOR_RESIDUAL_MLP_EXECUTION_ONLY, EXPLICIT_HOST_STAGED, POLICY_LIMIT_EXPERIMENT_NOT_PHYSICAL_CAPACITY_PROOF. Four physical 8 GB cards, a larger-than-hardware-capacity LLM, direct P2P, Intel execution and performance benefit remain separate gates.

Provider source and independent reviews are immutable under records/factory_runs. The implementing agent first tests the contract, then gates/corrects the candidate and runs hardware experiments. The lead reviews numerical evidence and failure controls before updating the acceptance verdict. Refusal or timeout artifacts are not working-executor PASS results.

The first Qwen MLP candidate failed static review: missing pure planning API, heuristic GPU selection with first-device fallback, absent independent CPU reference, and a hardcoded PASS/FAIL branch. It was not executed. An independent DeepSeek review confirmed the central defects, while several incorrect review claims were rejected. The in-house implementing agent was then authorized to build the specified executor from the contract, with external models reviewing that actual implementation. Do not describe the rejected source as a functioning executor merely because its provider request completed.
