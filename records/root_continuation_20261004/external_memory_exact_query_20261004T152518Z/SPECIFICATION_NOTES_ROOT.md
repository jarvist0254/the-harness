# Host and foreign-memory import prerequisites

Root read the current primary specification on October 4, 2026. This records API requirements; it does not certify installed hardware or a transfer.

The host-memory extension supports ordinary host allocations and host-mapped foreign memory as distinct handle types. Implementations can support either independently. Both allocation size and pointer alignment must satisfy the device's import alignment. Exporting these handle types is not supplied by this extension. Therefore querying exact per-handle buffer capabilities precedes any import. [Extension specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_external_memory_host.html).

An import must retain valid backing for its complete lifetime and explicitly synchronize host/device access. Importing the same backing into multiple Vulkan instances is permitted, with platform restrictions and potential import refusal. Host-visible memory types are the appropriate ordinary desktop path; non-host-visible imports have additional restrictions, including undefined content and restrictions on application access. An application must not concurrently access a different host alias of the same imported physical memory. [Import structure and rules](https://docs.vulkan.org/refpages/latest/refpages/source/VkImportMemoryHostPointerInfoEXT.html).

After a logical device exists, `vkGetMemoryHostPointerPropertiesEXT` must query the particular valid pointer and correct handle type. A positive physical-device capability query does not replace this pointer-specific memory-type selection or successful allocation/binding. A normal RAM pointer must not be mislabeled as foreign-device memory; a foreign mapping must genuinely satisfy that handle's requirements. [Pointer query](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetMemoryHostPointerPropertiesEXT.html), [allocation memory-type requirement](https://docs.vulkan.org/spec/latest/chapters/memory.html).

Any future ordinary-host import run will be classified as shared system backing. A foreign-device experiment requires independently justified exporter allocation, CPU mapping, compatible importer memory types, backing/lifetime and synchronization evidence. Neither successful import nor a device-local flag by itself establishes a measured Intel↔NVIDIA direct VRAM path, pooled memory or NVLink-equivalent coherence/performance.
