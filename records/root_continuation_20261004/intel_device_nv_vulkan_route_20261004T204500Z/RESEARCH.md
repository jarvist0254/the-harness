Duplicate it into an application-owned FD for an importer that consumes ownership; do not close the original. Retain Intel allocation/context until all consumer work and imported Vulkan memory are released.

## Vulkan normative issue to resolve before an import probe

[VkImportMemoryFdInfoKHR](https://docs.vulkan.org/refpages/latest/refpages/source/VkImportMemoryFdInfoKHR.html) VUID00668 says:

> The memory from which `fd` was exported must have been created on the same underlying physical device as `device`

The surrounding raw normative context is saved, not inferred from CUDA interoperability. [Vulkan v1.4.321 memory.adoc](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Docs/v1.4.321/chapters/memory.adoc):2326–2380 places the whole section under VK_KHR_external_memory_fd;00668 at2361 has no OPAQUE_FD condition. Next00669 explicitly permits OPAQUE_FD or DMA_BUF. [Current main](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Docs/main/chapters/memory.adoc):2584–2639 repeats the unconditional rule. These exact snapshots and hashes are in source_receipt.json. As written, an Intel-created DEVICE allocation and distinct NVIDIA consumer fail this requirement. Extension availability or memoryTypeBits cannot waive it. This prevents describing the proposed call as already conformant; it is not a blanket physical impossibility claim.

There is material contrary scope evidence. [DMA_BUF extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_external_memory_dma_buf.html) is expressly for Linux sharing across kernel drivers/processes and binding VkBuffer. [NVIDIA maintainer discussion243](https://github.com/NVIDIA/open-gpu-kernel-modules/discussions/243), Oct22,2024, reports foreign dma-buf imports via EGL/Vulkan through nvidia-drm PRIME rather than CUDA/resource-manager dma-buf code. That is a maintainer statement about driver support, not a tested Intel DEVICE allocation or normative exception. Current [NVIDIA nvidia-drm-gem.c](https://raw.githubusercontent.com/NVIDIA/open-gpu-kernel-modules/main/kernel-open/nvidia-drm/nvidia-drm-gem.c):136–162 falls through to drm_gem_prime_import for foreign ownership. This establishes an import mechanism, not arbitrary Intel VRAM reachability or absence of migrations. A main-branch snapshot is not bound to this machine's installed driver.

## Conditional importer sequence — not execution authorization

If Root resolves00668 with an applicable authoritative exception/correction or documented driver contract:

1. Require actual NVIDIA Vulkan extension support for VK_KHR_external_memory_fd, VK_EXT_external_memory_dma_buf and a foreign ownership mechanism. Require IMPORTABLE. This does not prove specific-FD acceptance.
2. Create buffer with VkExternalMemoryBufferCreateInfo(handleTypes=DMA_BUF). Query buffer memory requirements and dedicated requirements. [vkGetMemoryFdPropertiesKHR](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetMemoryFdPropertiesKHR.html) queries this Intel-produced DMA_BUF, providing compatible memoryTypeBits. Intersect those bits with buffer requirements and real NVIDIA memory types; zero intersection refuses. OPAQUE_FD is not a substitute. Obtain actual exported extent; require sufficient size/alignment, never guess allocation size from payload bytes.
3. Import only the duplicated application-owned FD using VkImportMemoryFdInfoKHR in VkMemoryAllocateInfo.pNext. Honor [DEDICATED_ONLY](https://docs.vulkan.org/refpages/latest/refpages/source/VkExternalMemoryFeatureFlagBits.html) and requiresDedicatedAllocation with VkMemoryDedicatedAllocateInfo(buffer). [Allocation rules](https://docs.vulkan.org/refpages/latest/refpages/source/VkMemoryAllocateInfo.html) require compatible descriptor/size/type choices. Successful import consumes FD ownership; failed import leaves the duplicate for checked close. Bind compatible imported memory; no unreported fallback allocation/copy.
4. Intel command-list fill writes a deterministic pattern; bounded fence waits complete producer work. Imported memory alone is not synchronization. Use [foreign queue ownership](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_queue_family_foreign.html) semantics documented for the actual driver, not EXTERNAL's same-device assumption. Acquire to NVIDIA transfer queue, GPU-copy into a distinct consumer-owned result buffer, then bounded fence/readback with correct transfer→host barrier/invalidate when noncoherent. Final CPU readback is verification only, not cross-device staging. Explicit cross-API coherency/ownership protocol must be reviewed before runtime; host waits alone do not establish cache visibility.
