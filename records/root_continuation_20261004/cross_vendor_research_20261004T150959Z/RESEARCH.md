# Cross-vendor transfer research: primary evidence and next gates

Scope: off-machine primary research, not hardware qualification. No downloads, installations, native probes, provider calls or GPU work were performed in this task.

## What has actually been demonstrated

**VERIFIED_PRIMARY_DESCRIPTION — Joint Training on AMD and NVIDIA GPUs.** The paper describes CUDA/ROCm adapters, ibverbs transport and NCCL/RCCL collectives. Its direct data path is GPU user buffer → GPU chunk buffer → NIC → network → other GPU chunk buffer → user buffer; CPU control coordinates registration and synchronization. Tests use two nodes, eight NVIDIA H200s and eight AMD MI325Xs, with eight BlueField-3 DPUs per node. Heterogeneity is confined to pipeline parallelism; tensor/data parallelism stays homogeneous. The authors report 98.2% LLaMA and 94.4% Qwen per-GPU throughput relative to the NVIDIA baseline; homogeneous DP4 uses eight GPUs whereas heterogeneous DP8 uses sixteen (both TP1/PP2). These throughput comparisons and 500-iteration training results apply to that configuration, not four consumer cards, Windows, inference, or pooled VRAM. **PUBLIC_CODE_NOT_FOUND_WITHIN_BOUNDS:** the full paper and three targeted GitHub searches did not reveal an author implementation; linked dependencies are not that implementation. [Full primary paper](https://arxiv.org/html/2602.18007v1).

**VERIFIED_PRIMARY_DESCRIPTION — dmaplane, with public author code.** The paper explicitly links its GPL-2.0 implementation. This is a Linux kernel DMA/RDMA experimentation framework with NUMA allocation, dma-buf attachment, verbs queues and NVIDIA peer-memory integration. Its SoftRoCE measurements and two-node KV-transfer demonstration use software RDMA: CPU copying remains involved. Hardware-NIC and NVIDIA BAR registration paths are described but are not an AMD–NVIDIA hardware-direct result. It is neither an LLM scheduler nor a demonstrated Windows backend. [Paper](https://arxiv.org/html/2603.10030v2), [author repository](https://github.com/marcoeg/dmaplane).

The inspected implementation builds a kernel module against Linux headers and conditionally includes GPU support when NVIDIA peer headers are found. Its GPU source calls NVIDIA peer-page APIs, maps BAR pages and exposes a contiguous CPU-accessible BAR mapping for SoftRoCE; fragmented mappings are refused for that path. These inspected files establish a real NVIDIA-specific implementation, not an AMD adapter or a completed security/quality audit. No repository code was executed. [Driver build](https://raw.githubusercontent.com/marcoeg/dmaplane/main/driver/Makefile), [actual GPU implementation](https://raw.githubusercontent.com/marcoeg/dmaplane/main/driver/gpu_p2p.c).

**VERIFIED_PRIMARY_DESCRIPTION — official AMD consumer RDMA evidence.** ROCm XIO documents Radeon RX 9070 XT GPU-initiated RDMA WRITE tests on Ubuntu with ROCm 7.2 and Broadcom/Pensando NICs. LFSR verification checks distinct iteration seeds. Queue location and payload location vary separately: a GPU-launched operation alone does not prove a VRAM-resident payload. The measurements are single-operation NIC-loopback tests, not a cross-vendor model pipeline. Sizes below 32 bytes are a documented hang risk. This is useful consumer-GPU evidence, but does not qualify this host's gfx1036 integrated GPU or Windows. [Official test environment and verification](https://rocm.docs.amd.com/projects/rocm-xio/en/beta-0.1.0/reference/performance.html).

XIO's installation instructions support Linux and require ROCm/HSA, libdrm and suitable networking/kernel facilities. The inspected verbs wrapper uses libibverbs and supports dma-buf registration as well as fallback registration; success alone cannot identify the payload's backing. NIC-specific prerequisites can include patched drivers. This is an actionable public source route for a separately approved Linux/NIC experiment, not a portable Windows extraction or current installed capability. [Official installation](https://raw.githubusercontent.com/ROCm/rocm-xio/main/INSTALL.md), [actual verbs implementation](https://raw.githubusercontent.com/ROCm/rocm-xio/main/src/common/ibv-wrapper.cpp).

**VERIFIED_PRIMARY_DESCRIPTION — legacy DirectGMA.** AMD's public samples require two AMD GPUs with DirectGMA support and expose OpenCL/OpenGL/DX11 paths. The README's Windows setup targets FirePro controls and old SDK/build environments. Actual OpenCL code creates bus-addressable local buffers, obtains resident bus addresses and creates external-physical AMD buffers with marker synchronization. This is vendor-specific explicit buffer addressing, not an AMD–NVIDIA example, and current consumer-driver compatibility is unverified. No settings were changed. [Official sample](https://github.com/GPUOpen-LibrariesAndSDKs/DirectGMA_P2P), [actual OpenCL buffer implementation](https://raw.githubusercontent.com/GPUOpen-LibrariesAndSDKs/DirectGMA_P2P/master/GPUtoGPU_OpenCL/GPUtoGPU_OpenCL/CLTransferBuffer.cpp).

## API prerequisites and limits

NVIDIA GPUDirect RDMA needs compatible peer hardware, registration/driver integration and suitable PCIe topology. The documentation discusses a shared upstream PCIe root complex and warns that external DMA completion alone does not establish CUDA execution visibility; synchronization is essential. These requirements have not been satisfied or tested for the current RTX 5070 Ti. AMD's PeerDirect documentation similarly describes ROCm-aware communication and driver/NIC integration, not universal support for every AMD allocation. [NVIDIA prerequisites and ordering](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html), [AMD GPU-enabled communication](https://instinct.docs.amd.com/projects/cluster-documentation/latest/how-to/gpu-enabled-mpi.html).

CUDA's Vulkan external-memory/semaphore interop requires matching physical-device UUIDs. It therefore does not establish a way to import another vendor's Vulkan device-local allocation into CUDA. Vulkan external handle compatibility must be checked for the particular device, driver and handle type. [CUDA same-device rule](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/graphics-interop.html), [Vulkan identity/compatibility](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceIDProperties.html).

VK_EXT_external_memory_host permits importing ordinary host allocations or host-mapped foreign-device memory, depending on implementation support. It requires per-handle importability, memory-type queries, alignment and lifetime/synchronization compliance. Foreign mapping import is an interesting experimental route, but the extension does not promise a coherent VRAM pool or transparent arbitrary Python tensors. [Official host import specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_external_memory_host.html).

## Current host evidence and proposed gated tests

**WINDOWS_TARGET_UNCHECKED / HARDWARE_MISSING for enterprise RDMA qualification.** This task did not inspect installed NICs or PCIe routing. The proposed four external 8 GB cards are not the measured paper population; the existing display GPU remains separate. A single current NVIDIA device cannot qualify an inter-NVIDIA link, and integrated/shared AMD memory must not be counted as dedicated VRAM.

The existing local capability query timed out after 30.032 seconds. Its partial output reports NV/AMD external-host/Win32 memory and semaphore extensions and 4096-byte host-pointer alignment. HOST_ALLOCATION/HOST_MAPPED_FOREIGN import feature results, actual imports and OpenCL external-handle support remain NOT_CHECKED. Extension strings are not import proof. Source: ../external_memory_capability_20261004T144953Z/capability_result_report.md and its raw receipt/stdout.

1. On the current Windows host, first query both devices' exact external-buffer handle import features and memory-type masks with a bounded API fixture. Refuse unsupported/unknown results. Then, if admitted, import one aligned ordinary host allocation independently into both devices, with explicit ownership and synchronization, no greater than 1 MiB. Check a full deterministic byte pattern in each direction and a corrupted-data control. Classify success as shared host backing with explicit transfers; do not call it VRAM pooling.
2. Only after that succeeds, separately query HOST_MAPPED_FOREIGN support and the exporter's valid CPU mapping/lifetime. A scoped foreign-allocation experiment must verify both GPU readbacks, exact bytes, synchronization and release order. Unsupported imports are NOT_CHECKED/refused, not an invitation to reinterpret a CPU pointer as peer VRAM. Dynamic topology and native-driver safety require a fresh admission.
3. With two actual GPUs visible in a single CUDA or HIP runtime, query directional peer-access capability and identity before enabling anything. Test a small copied tensor, full parity and corruption, with bounded synchronization. A positive same-vendor link says nothing about cross-vendor links. [CUDA peer queries](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__PEER.html), [HIP peer queries](https://rocm.docs.amd.com/projects/HIP/en/latest/doxygen/html/group___peer_to_peer.html).
4. A separate Linux RDMA experiment requires physically present supported GPU/NIC pairs, kernel/driver support and registration evidence before allocating GPU payloads. Begin with at least 256 bytes, up to 1 MiB, record payload/queue backing separately, enforce deadlines and use full LFSR/byte parity plus a real corruption control. Only a tested AMD-to-NVIDIA endpoint pair can qualify that direction. Installing Linux modules or changing NIC drivers is outside this task.

Engineering assessment: the papers support the possibility of explicit heterogeneous pipeline execution and device-direct networking under specified prerequisites. Resident layers in separate vendor contexts with explicit host-staged activation transfers remain a credible experimental baseline for the four-card design. They can demonstrate numerical execution, placement and transfer counts; greater-than-single-card capacity needs actual simultaneous resident allocations and one/three-card refusal controls. None of these results would establish coherent pooled VRAM, arbitrary Python compatibility, production load/contact safety, or acceptable LLM performance.
