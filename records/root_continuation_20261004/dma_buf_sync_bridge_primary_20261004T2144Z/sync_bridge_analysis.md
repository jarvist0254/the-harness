# DRM sync_file → EGL native fence bridge: source audit

Research completed 2026-10-04. This is a specification/source audit only. No GPU, driver, compiler, EGL context, or provider was invoked. The downloaded primary-source files and their hashes are listed in `source_manifest.json` (eight snapshots; each is under 1 MiB).

## Finding

The standards provide a way to order work across APIs **when both sides exchange a sync-file fence that represents the relevant work**. They do not create a Level Zero completion fence from a host event, attach that fence to a dma-buf reservation automatically, or guarantee that an arbitrary NVIDIA EGL import observes writes made by an Intel Level Zero device. The candidate bridge therefore remains `NOT_CHECKED` until a driver-supported producer-fence export and cross-driver visibility contract are demonstrated.

## Keep the FD types and provenance distinct

Linux DRM has two meanings for a syncobj FD. The default `DRM_IOCTL_SYNCOBJ_HANDLE_TO_FD` result is an **opaque syncobj FD**, useful for transferring/reference-counting the same syncobj. With `DRM_SYNCOBJ_HANDLE_TO_FD_FLAGS_EXPORT_SYNC_FILE`, it instead exports a new **sync_file FD** for the syncobj's current fence. The export snapshots the fence currently attached to that syncobj; resetting or signaling the syncobj later does not change the exported sync_file. The reciprocal `DRM_IOCTL_SYNCOBJ_FD_TO_HANDLE` import flag imports a sync_file as the syncobj's current fence. See [DRM synchronization objects](https://docs.kernel.org/gpu/drm-mm.html#drm-sync-objects), rendered source lines 9621–9625; this audit's unrendered official RST source is pinned in `drm-mm-main.rst`.

A syncobj export does not make its fence represent Level Zero work merely because the application calls it after `zeEventHostSynchronize`. The fence must already be the actual completion fence for the producer submission. A freshly created or host-signaled syncobj, an EGL fence in an unrelated GL context, or a completed CPU event without a queue-to-syncobj linkage has the wrong provenance and can pass a false-green test.

The dma-buf `DMA_BUF_IOCTL_EXPORT_SYNC_FILE` is different again: it snapshots the dma-buf reservation object's **current fences**, filtered by READ/WRITE usage. A READ export waits for writers; a WRITE export waits for readers and writers. `DMA_BUF_IOCTL_IMPORT_SYNC_FILE` installs a sync_file as a read or write fence for later implicitly synchronized users. Kernel documentation describes the explicit/implicit bridge as: export existing reservation fences, make explicit work wait for them, create a completion sync_file for that work, then import that completion fence back into the reservation for later implicit users. The export/import sequence is not atomic; callers must serialize reservation changes/submissions so another user cannot add a fence between the snapshot and import. See [dma-buf synchronization](https://docs.kernel.org/driver-api/dma-buf.html#dma-buf-implicit-fencing), rendered lines 182–202 and 223–234.

Therefore a dma-buf reservation export is useful only if the Level Zero producer's real completion fence is actually present in that reservation. No examined Level Zero API or the pinned Intel runtime source establishes that automatically. Do not export a possibly empty/stale reservation after a host wait and label it the producer fence.

## EGL native-fence requirements and ownership

`EGL_ANDROID_native_fence_sync` allows `eglCreateSyncKHR` to import a native fence FD as an EGL sync object. The EGL implementation takes ownership of a nonnegative FD passed as `EGL_SYNC_NATIVE_FENCE_FD_ANDROID`; the caller must stop using it after the call. Keep a separate `dup` if another consumer still needs an FD. Destroying the imported EGL sync closes its owned FD. `eglDupNativeFenceFDANDROID` returns a new owned FD for an EGL sync that has a native fence; the receiver must close it. These are native-fence FD ownership rules, not dma-buf or DRM-syncobj FD rules. See [EGL_ANDROID_native_fence_sync](https://registry.khronos.org/EGL/extensions/ANDROID/EGL_ANDROID_native_fence_sync.txt), especially the FD attribute and ownership language at extension lines 83–110, 177–204, and 220–224.

Import requires a current client-API context and a matching EGLDisplay; the extension reports `EGL_BAD_MATCH` when there is no suitable current context/display/API. Creating a native-fence sync with `EGL_NO_NATIVE_FENCE_FD_ANDROID` inserts a fence into the current client API command stream. It says when that EGL/GL stream reaches the fence; it cannot retroactively stand for Level Zero work. Before attempting import, enumerate/query the actual EGL device/display and verify the selected implementation advertises the required device-query/DRM-render-node and native-fence extensions. For an EGL consumer that needs a GPU-side wait, verify `EGL_KHR_wait_sync` and the relevant client API sync support on that actual display/context.

`eglWaitSyncKHR` is a server wait: it returns to the host without waiting for completion and orders subsequent work in the current EGL context. Its implementation may use CPU or GPU mechanisms. It is not a bounded host-completion test. Use a separate finite `eglClientWaitSyncKHR`/EGL client wait for host observation, check timeout/error returns, and enforce an external deadline. See [EGL_KHR_wait_sync](https://registry.khronos.org/EGL/extensions/KHR/EGL_KHR_wait_sync.txt), lines 82–122, and [EGL 1.5 client wait](https://registry.khronos.org/EGL/specs/eglspec.1.5.pdf), §3.8.4.

## Level Zero ordering/coherency is local API evidence, not foreign EGL visibility

`zeCommandListAppendBarrier` appends an execution and global memory barrier for the command list/queue; it orders the prior work and subsequent work in that Level Zero submission. It does not export a Linux sync_file or attach a fence to a dma-buf reservation. See the pinned [Level Zero command-list reference](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/command_list.html#zecommandlistappendbarrier), local snapshot lines 887–897.

`zeEventHostSynchronize(event, finite_timeout)` blocks the calling host thread and has a finite-timeout result (`ZE_RESULT_NOT_READY` if it has not signaled); do not use `UINT64_MAX` for a bounded smoke. Event signal/wait scopes describe Level Zero cache flush/invalidate behavior. In particular, `ZE_EVENT_SCOPE_FLAG_DEVICE` covers global device access and peer-device access within the Level Zero model; `ZE_EVENT_SCOPE_FLAG_HOST` covers device/host coherency. Default scope zero supplies no additional flush/invalidate. See the pinned [Level Zero event reference](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/event.html#zeeventhostsynchronize), local snapshot lines 824–835 and 1513–1516, and the [Programming Guide event-scope examples](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/PROG.html), local snapshot lines 3967–3990.

Those scope guarantees do not state that an unrelated NVIDIA EGL driver will invalidate its cache for Intel Level Zero writes. Linux dma-buf sync-file establishes ordering/completion dependencies, not a cross-vendor cache-maintenance or physical-visibility promise. `DMA_BUF_IOCTL_SYNC` is for CPU access cache-coherency and does not synchronize device work; it is not a substitute for the missing GPU-to-GPU contract. No cited API proves physical VRAM peer access, residency, no staging/migration, or direct P2P.

## Conditional legal sequence for a future test

1. Identify the exact Intel Level Zero producer, shared allocation/dma-buf, NVIDIA EGL device/display, and their driver/device identities. Fail closed if required import, semaphore, or native-fence extensions are absent.
2. Submit a deterministic Level Zero write to the shared allocation. Signal a Level Zero event only after that command completes; choose the documented event scope needed for the intended Level Zero visibility and wait with a finite host timeout. This proves the producer work completed under Level Zero, not that a foreign NVIDIA consumer sees it.
3. Continue only if a documented/runtime-verified mechanism turns that exact submission completion into a Linux sync_file. A queue-scheduled DRM syncobj fence exported with `EXPORT_SYNC_FILE` could serve if the driver exposes this linkage. A dma-buf reservation fence could serve only if the producer truly installed its fence in the reservation. The currently inspected Intel external-semaphore host path performs DRM syncobj FD operations on the host and does not schedule a command-list signal, so it does not itself provide this linkage.
4. If using dma-buf reservation sync-file export/import, serialize fence snapshots and imports against all other reservation users. Preserve sync_file vs opaque syncobj FD types and apply the correct FD ownership for each API boundary.
5. Import the real producer sync_file into a current NVIDIA EGL context on its matching display using `EGL_ANDROID_native_fence_sync`; queue the consumer behind `eglWaitSyncKHR` only after confirming extension/context support. Consume/validate the shared payload with the NVIDIA GPU. Use finite host-side waits to bound producer and consumer completion. If returning ownership to an implicit consumer, export/import the actual NVIDIA completion fence through the reservation under the same serialization discipline.
6. Compare the full payload against an independent CPU reference, with stale/pre-signaled-fence negative controls that prove the consumer cannot pass before the producer's genuine completion fence.

## Gates still open

- A real Level Zero submission-to-syncobj/sync_file or reservation-fence path, with exact fence provenance and correct failure behavior.
- NVIDIA EGL device/display/context and extension availability on this host, and valid EGL import of the shared allocation.
- Driver-supported cross-driver cache visibility for this allocation and direction. Completion ordering alone is insufficient.
- Correct reservation serialization, bounded waits, and FD ownership on both success and all error paths.
- Actual full-byte producer/consumer parity plus stale-fence and corruption controls.
- Backing classification and topology. A successful test could prove this tested transfer path only; it would not prove physical VRAM residency or direct P2P.

The pinned Intel runtime source trace at `records/root_continuation_20261004/l0_fd_sync_bridge_trace_20261004T2115Z/bridge_contract_findings.md` is supporting implementation evidence, not a portable contract: its Linux external-semaphore code imports/exports syncobj handles through DRM ioctls on the host, closes imported sync-file FDs, and does not accept a Level Zero queue/list completion object for scheduling a GPU signal. Its boolean error result was not propagated by the inspected wrapper. That leaves the L0-to-kernel-fence linkage as an unresolved prerequisite rather than a demonstrated bridge.
