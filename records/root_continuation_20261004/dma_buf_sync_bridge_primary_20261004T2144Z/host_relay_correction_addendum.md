# Correction: a post-completion CPU fence relay is a valid ordering design

This addendum narrows the earlier `sync_bridge_analysis.md` gate. Requiring a queue-scheduled Level Zero → DRM syncobj fence is too strong for every possible experiment. A **control-plane-only host relay** can legally order a later consumer without copying the payload through CPU memory:

1. Submit the producer write on the Level Zero queue with a Level Zero fence/event tied to that submission. Wait with a finite timeout and continue only after the driver reports successful completion. Choose the documented Level Zero signal scope needed for the producer-side cache contract.
2. Only after that success, signal a fresh/reset DRM syncobj from the host with the corresponding `DRM_IOCTL_SYNCOBJ_SIGNAL` (or exact timeline point through `DRM_IOCTL_SYNCOBJ_TIMELINE_SIGNAL`). Then export its current fence as a `sync_file` using `DRM_SYNCOBJ_HANDLE_TO_FD_FLAGS_EXPORT_SYNC_FILE`.
3. Import the resulting already-signaled native sync-file FD into the selected NVIDIA EGL context using `EGL_ANDROID_native_fence_sync`. The application must not start the consumer before the producer wait and successful signal/export/import sequence complete. Keep this result labeled `CPU_RELAY_AFTER_L0_COMPLETION`: the CPU signal is a relay of a completed producer stage, not a native queue-scheduled fence and not evidence of an asynchronous cross-driver semaphore.
4. Leave the shared payload in its shared allocation. Do not read/copy the payload on CPU for the relay. Continue to treat allocation import, cross-driver visibility/cache maintenance, backing, and physical P2P as separate unresolved questions.

The pinned Intel runtime source illustrates that a host-side syncobj signal ioctl exists: `shared__source__os_interface__linux__external_semaphore_linux.cpp` (SHA-256 `f4e9e16b9deea753720ab85156cbe69795c70aded895910e07632e8f7d55711f`) invokes `syncObjTimelineSignal` at lines 121–132 or `syncObjSignal` at lines 133–142, and returns `false` on ioctl failure. Those lines show a host ioctl only; they do **not** bind the signal to a queue completion. The ordering proof must come from the application sequence: the exact producer fence/event returned success before the CPU invokes the signal. A signal created before producer completion, a dummy fence, or a stale syncobj state remains invalid as producer evidence.

The Linux DRM documentation describes exporting the current syncobj fence as a sync-file snapshot ([DRM synchronization objects](https://docs.kernel.org/gpu/drm-mm.html#drm-sync-objects)); the extension contracts do not prohibit an application from signaling a syncobj after its separately verified producer wait. Thus the host relay removes the need for a queue-to-syncobj export facility for a **serialized control-plane experiment**. It does not solve a producer-completion timeout safely by itself: on timeout, do not signal or hand ownership to the consumer, and do not destroy objects while work may still be pending without a documented cleanup/drain path.

This correction does not change the separate `DMA_BUF_IOCTL_EXPORT_SYNC_FILE` reservation-fence caveat: that ioctl snapshots fences already present in the dma-buf reservation and cannot be assumed to find Level Zero work unless the producer actually attached its fence there. If using the host relay directly for an explicit EGL consumer, the signaled sync-file can be imported as the EGL native fence without exporting the dma-buf reservation. If bridging later implicit users, import/export reservation fences with the kernel-documented serialization needed to prevent races.

Remaining gates are unchanged: demonstrate actual selected-device EGL import and shared allocation support; preserve exact FD ownership and error handling; validate full payload from the consumer GPU; ensure cross-driver cache visibility for the shared object; and make truthful backing/topology claims. A passing CPU-relay experiment would establish the serialized order and measured payload result for that tested setup only. It would not establish direct P2P, VRAM residency, or an asynchronous GPU-to-GPU fence bridge.
